# Brigade

An implementation of the [Relay Method](https://a4al6a.substack.com/p/the-relay-method) — a multi-agent software-development workflow.
It splits AI-assisted development across specialised roles arranged in a line, each allowed to talk only to its neighbours, plus a Designer reachable directly from the Interpreter for visual exploration, and a Sentinel that audits the whole ledger outside the chain:

```
Owner (human) ⇄ Interpreter ⇄ Analyst ⇄ Examiner ⇄ Builder
                       ⇅
                    Designer          Sentinel (audits all)
```

Each role reasons at a different level of abstraction, and every message between them is written once to a permanent ledger, so the whole trail from a human's problem statement down to real executed evidence is replayable and auditable.

| Role | What it does | Touches code? |
|---|---|---|
| **Owner** | The human. States problems, approves roadmaps, gates increments. | no |
| **Interpreter** | The coding harness itself. Restates problems as *needs* and talks to the Owner. | no |
| **Analyst** | Turns a need into an observable *behaviour* (what must be true, never *how*). | no |
| **Examiner** | Decomposes a behaviour into checkable *expectations*, then judges evidence and issues a verdict (Expectation-Driven Development). | no |
| **Builder** | Implements expectations in an isolated worktree and reports real executed evidence. | yes |
| **Designer** | Generates exploratory HTML/CSS concept directions, reviewed and iterated on by the Owner. | yes (visual shell only) |
| **Sentinel** | Periodically audits the ledger for contract violations and surfaces advisories. | no |

The Interpreter is **not** a separate process — it is the coding harness you already use (`claude` or `opencode`), configured to behave as the Interpreter via an `AGENTS.md` persona and an MCP server.
The Analyst, Examiner, Builder, and Designer each get their own configurable model.
The Sentinel is an auditor outside the chain — it only reads the ledger and writes `advisory`/`warning` flags; it never intervenes.

## Installation

Brigade is a Python CLI distributed via `uv`.
It is not published to PyPI yet — install it directly from a local checkout (or a git URL):

```bash
uv tool install /path/to/brigade            # from a local checkout
# or, once it's in a repo:
uv tool install git+https://github.com/you/brigade
```

This builds the package and puts the `brigade` command on your `PATH`.

After changing the source, reinstall to pick up the changes:

```bash
uv tool install --reinstall /path/to/brigade
```

Requires Python 3.10+ and `uv`.

## Quick start

1. **Install** the CLI (see above).

2. **Scaffold** a project:

   ```bash
   brigade init myproject
   cd myproject
   ```

   This creates the `.brigade/` state directory, `.mcp.json`, `opencode.json`, `AGENTS.md`, a `.gitignore`, and initialises a git repository.

3. **Configure models** in `.brigade/config.toml` (see [Configuration](#configuration)) and export the API keys as environment variables:

   ```bash
   export DEEPSEEK_API_KEY=sk-...     # or ANTHROPIC_API_KEY / OPENAI_API_KEY / OPENROUTER_API_KEY
   ```

4. **Start the workers and dashboard** (one terminal, in the project directory):

   ```bash
   brigade up
   ```

   This validates the config, starts the role workers, and opens the live dashboard (see [Live dashboard](#live-dashboard)).

5. **Start the harness** (another terminal, same directory):

   ```bash
   claude        # or: opencode
   ```

   It picks up `.mcp.json` / `opencode.json` and `AGENTS.md` automatically.

6. **Talk to it.** State a problem in plain language.
   The Interpreter asks clarifying questions, proposes a roadmap, gets your verdict, then dispatches behaviours one at a time and reports back increments.

## Configuration

Configuration lives in `.brigade/config.toml`, generated by `brigade init`:

```toml
[project]
max_loops = 3                      # cap on the expectation → evidence → verdict loop
model_timeout_seconds = 120        # per model-call timeout; a [roles.<role>] override wins

[roles.analyst]
model = "deepseek/deepseek-v4-flash"

[roles.examiner]
model = "deepseek/deepseek-v4-pro"

[roles.builder]
model = "deepseek/deepseek-v4-pro"
harness = "opencode"               # "claude" or "opencode" — the coding harness the Builder spawns

[roles.designer]
model = "deepseek/deepseek-v4-pro"
harness = "opencode"               # "claude" or "opencode" — the harness that generates visual concepts
review_tool = "auto"               # "auto" | "lavish" | "basic" — how the Owner reviews the concept

[roles.sentinel]
model = "anthropic/claude-sonnet-5"
scan_every = 10                    # run a scan after this many new ledger messages

[capabilities.model_overrides]
# escape hatch — fill in only when the built-in capability table is wrong
# "some/model" = { structured_output = "loose" }
```

- **`model`** strings are `provider/model` (LiteLLM-style), e.g. `anthropic/claude-sonnet-5`, `deepseek/deepseek-v4-pro`, or `openrouter/deepseek/deepseek-v4-pro`.
- **API keys never go in config** — they come from the environment, using the standard per-provider variable names (`DEEPSEEK_API_KEY`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `OPENROUTER_API_KEY`).
- **`[roles.builder].harness` is required** when the builder role is configured.
- **`[roles.designer].review_tool`** selects how the Owner reviews generated concepts — `lavish` (lavish-axi), `basic` (browser + the `brigade up` terminal), or `auto` to pick based on what's on `PATH`.
- **`[roles.sentinel].scan_every`** controls how often the auditor scans (in new-ledger-message counts). Recommend configuring the Sentinel to a *different* model than the rest of the pipeline — an auditor sharing blind spots with what it audits is a weaker auditor.
- **`[project].model_timeout_seconds`** (default `120`) bounds each model call; a `[roles.<role>].model_timeout_seconds` override wins for that role. A timeout is retried like any transient failure rather than treated as fatal.
- The `[roles.interpreter]` role needs no model — the Interpreter is the harness itself.

### Model capabilities

A small built-in table tracks whether each provider supports structured output: Anthropic and OpenAI are treated as `strict`, Deepseek as `loose` (JSON mode only, no native JSON schema), and anything unknown falls back to `none` (freeform output, parsed and retried).
The `strict` tier is real: those models receive the pydantic schema as provider-native constrained decoding, with a fallback to plain JSON mode if the provider rejects the schema.
`[capabilities.model_overrides]` is the escape hatch to correct a missing or wrong entry.

## CLI reference

| Command | Description |
|---|---|
| `brigade init [DIR]` | Scaffold `.brigade/` and harness files into a new or existing directory (defaults to `.`). Refuses to overwrite unless `--force`. |
| `brigade up` | Validate config, start the workers, and launch the live TUI dashboard. `--quiet` / `--verbose` control log verbosity. |
| `brigade status` | Show inbox depths and project state. |
| `brigade down` | Stop workers (stub — no daemonised workers yet). |
| `brigade mcp` | Run the Interpreter MCP server over stdio (spawned by the harness, not called directly). |

## Live dashboard

`brigade up` launches a live Textual dashboard in the terminal (not a headless process).
It is built entirely on the existing `logging` stream via a custom handler — no parallel event system, and no change to how workers do their work.

Four screens:

| Key | Screen | What it shows |
|---|---|---|
| *(default)* | Overview | The pipeline diagram plus a per-role table (`ROLE / STATUS / BEHAVIOUR / COST`). |
| `b` | Behaviours | Every behaviour with ledger activity, most-recent first, with status and stage. |
| `enter` | Ledger | The ledger for the selected behaviour, with each harness log reference. |
| `f` | Flags | The same Sentinel flag counts as `brigade status` (advisory vs warning). |

`q` (or `Ctrl+C`) quits.
Dollar cost is never stored — the Overview table computes it at render time from litellm's current pricing, accumulating each role's own token usage.

## Reliability and observability

Failures are surfaced rather than hidden inside worker threads:

- **Fail-fast config validation.** Before starting anything, `brigade up` checks every role it will run: a model is configured, it is in `provider/model` form, and its API key is present in the environment. All problems are reported together and the command exits nonzero; an unknown provider only warns.
- **Model-call timeout.** Every model call is bounded by `model_timeout_seconds` (default `120`). A timeout is retried like any transient failure and logs a `model_timeout` warning per attempt.
- **Worker error surfacing.** Each worker logs `worker_start` and `worker_exit` around its loop, catches per-message errors (logging the full traceback to `brigade.log` and continuing), and the dashboard marks a failed role in red (`ERROR`, `CRASHED`, or `stopped`).
- **Liveness.** The dashboard checks each worker thread once per second; a worker whose thread died without logging `worker_exit` renders as `DIED (no exit logged)`.
- **Crash-safe processing.** Claiming a message moves its pointer into an `in-progress/` staging dir; it is only cleared once the reply is delivered. A worker that dies mid-processing leaves the message recoverable, and the next startup moves it back into the inbox.

While the dashboard owns the terminal, the process's real stdout/stderr are redirected to `.brigade/logs/stray-output.log`, so third-party output can't corrupt the display.
Worker tracebacks go to `.brigade/logs/brigade.log` (via each role's logger), not `stray-output.log`.
A non-empty `stray-output.log` is therefore a diagnostic: something bypassed structured logging entirely.

## How a behaviour flows

1. The Owner states a problem to the Interpreter.
2. The Interpreter asks clarifying questions, proposes a roadmap, and waits for a `roadmap-verdict`.
3. On approval, the Interpreter dispatches one behaviour at a time via `dispatch_behaviour`.
4. The Analyst turns the behaviour into observable terms, stripping all implementation detail.
5. The Examiner decomposes it into checkable expectations (`E1..En`) plus one integration expectation.
6. The Builder implements the expectations in a git worktree (`.brigade/work/<behaviour_id>/`, branch `brigade/<behaviour_id>`) and runs real tests.
7. The Builder reports `evidence` with actual execution receipts — a `command` and captured `raw_output`, each tagged with a confidence tier (`executed`, `partial`, or `narrative`).
8. The Examiner judges the evidence and issues either a `verdict` (unmet expectations, loop count incremented) or a `behaviour-status` (`solved`, `blocked`, or `partial`).
9. The status climbs back up to the Interpreter, which presents the increment to the Owner.

The `expectation → evidence → verdict` loop is capped at `max_loops` (default 3).
On cap-out the Examiner escalates `blocked` upward instead of looping forever.

## Design exploration

When the Owner asks *what something should look like* rather than *what it should do*, the Interpreter routes it through the Designer instead of the Builder:

1. The Interpreter dispatches the request via `dispatch_design_request`.
2. The Designer generates a runnable HTML/CSS concept in its own worktree (`.brigade/work/<behaviour_id>-design/`).
3. The Owner reviews the concept through the configured adapter and gives feedback.
4. The Designer regenerates in place, same worktree, until the Owner approves or the `max_loops` cap is hit.
5. The approved concept's `artifact_ref` is folded into the eventual `behaviour-to-implement`, so the Builder can see the agreed design while it works.

The review is a live, synchronous loop (not mailbox-routed), and hitting `max_loops` without approval surfaces an explicit "proceed as-is or abandon" choice to the Owner — never a silent finalization.

## Interpreter classification (read vs change vs design)

Not every message enters the pipeline. The Interpreter classifies each Owner message before responding:

- **Read-only question** ("how do I run this", "what does this function do") — answered directly with the harness's own read tools; no `dispatch_behaviour`, no worker activity.
- **Code change** — even a one-line change — always routed through `dispatch_behaviour`. The Interpreter never edits project code itself.
- **Visual/creative direction** — routed through `dispatch_design_request`.
- **Ambiguous bug-report** ("why doesn't X work") — investigated and answered first, then the Owner is asked whether to dispatch a fix; never auto-dispatched.

Direct answers are still logged to the ledger via `log_conversation` (`question`/`result`), so the conversation stays replayable even without a pipeline run.

**Enforcement is persona-only.** The brigade package does not scope the harness's own file-write tools — the "never edit project code directly" guarantee is enforced by the Interpreter persona (`AGENTS.md`), not by a hard permission. This means the guarantee is as strong as the model's instruction-following: a stronger model honors it reliably, a weaker one may drift. Hard tool-level scoping would require harness-specific permission configuration and is left to the operator.

## The ledger

Every message is written once to `.brigade/ledger/<ulid>.json` — a permanent, git-committed audit trail.
Mailboxes (`.brigade/mailboxes/`) are transient pointer files, gitignored.
The ledger files sort chronologically by their ULID id, so the whole conversation can be replayed in order.

## Personas

Each role has a persona prompt defining its identity, allowed neighbours, forbidden-leakage boundaries, and output contract.
Built-in defaults ship with the package.
To override one, drop a file at `.brigade/personas/<role>.md` (`analyst`, `examiner`, `builder`, or `designer`).

## Development

```bash
uv sync --extra dev        # install the package + dev dependencies (pytest)
uv run pytest              # run the full test suite
```

The tests cover the message envelope and validator, the ledger and mailbox primitives, the config/capability/persona loading, the TUI bridge and dashboard screens, and each worker, using fakes for the LLM router and harness so no API keys are needed.
